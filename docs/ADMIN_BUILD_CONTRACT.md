# ECRN admin build: shared contract for parallel builders

Read this whole file before writing code. Several builders work in this repo **at the same time**, so the rules about file ownership are strict.

## Product context

ECRN is a referral network + job board for electrical construction, run by **Delta Construction Partners** (about 30 recruiters). Members sign up, apply to jobs, and refer people. The **admin side is for the company owners only** (role `admin`). It must show everything happening in the app and be ready to mirror Staffing Referrals / Bullhorn (no Bullhorn API access yet, so integrations are built "ready to plug in").

Two ideas drive the admin side:

1. **Attribution:** which Delta recruiter got each person to sign up. Each team member has a personal code (`staff.invite_code`, link `https://ecrn.com/r/CODE`). `profiles.recruited_by_staff_id` + `profiles.signup_source` (`recruiter` = direct via code, `member_invite` = invited by a member whose recruiter gets network credit, `organic`).
2. **Routing:** every sign-up, referral and application goes to the **account manager who owns the job**, who gives it to one of their recruiters. `jobs.account_manager_id`; `candidates.account_manager_id / recruiter_id / routing_reason`; `job_applications` and `job_referrals` each have `account_manager_id / recruiter_id`. Database triggers route automatically (see `supabase/migrations/0008_team_attribution_routing.sql`); admins can reassign with RPC `admin_assign`.

## Stack and conventions

- Next.js **16** App Router, React 19, TypeScript strict, Tailwind 3. Hosted on Cloudflare Workers (OpenNext), so: **no Node-only APIs** (`fs`, `child_process`), no new npm dependencies (already installed and allowed: `lucide-react`, `zod`, `qrcode-generator`, `@supabase/supabase-js`, `@supabase/ssr`).
- `params` and `searchParams` are **Promises**: `export default async function Page({ params, searchParams }: { params: Promise<{ id: string }>; searchParams: Promise<{ q?: string }> })`.
- Pages are **server components**. Use client components (`"use client"`) only for real interactivity. State that can live in the URL (filters, tabs, search, page) should use `searchParams` + plain `<form method="get">` / `<Link>`.
- Data access: `const sb = await createSupabaseServerClient()` from `@/lib/supabase/server`. Queries run as the signed-in user; Row Level Security gives admins full read/write on admin tables. Every admin page/action must start with `await requireAdmin()` (from `@/lib/auth/session`; it redirects non-admins).
- Mutations: **server actions** (`"use server"`), validate input, call Supabase, `revalidatePath(...)`, then `redirect(...)` or return a small result object. Errors shown via `?error=` in the URL or returned message. Never trust client input; re-check `requireAdmin()` inside every action.
- Types live in `types/index.ts`; row mappers in `lib/data/mappers.ts` (`toProfile`, `toCandidate`, `toJob`, `toStaff`, `toApplication`, `toJobReferral`, `toReferral`, `toPayout`, `toActivity`, `toCompanyLead`, `one`). Existing data functions: `lib/data/repository.ts` (read it before writing a query that may already exist).
- Team helpers: `lib/admin/staff.ts` → `listStaff()`, `getStaffMap()`, `getStaffById()`, `staffName()`, `STAFF_ROLE_LABEL`, `splitStaff()`, `inviteUrl(code)`.
- Admin UI kit (use it so every screen matches): `components/admin/ui.tsx` → `AdminPage`, `AdminHeader`, `Panel`, `StatCard`, `DataTable` + `tdClass`, `EmptyState`, `FilterTabs`, `Pill`, `Notice`, `fmtNum`, `fmtMoney(cents)`, `fmtPct`, `fmtDate`, `fmtDateTime`, `relTime`, `titleCase`.
- Charts (server-rendered SVG/CSS, no library): `components/admin/charts.tsx` → `Donut`, `BarList`, `ColumnChart`, `Funnel`, `StackedBar`, `Sparkline`, `Legend`, `KeyValues`, `CHART_COLORS`.
- Other UI: `components/ui/Button.tsx` (variants `primary | secondary | ghost | danger | dark | deep | soft`, sizes `sm | md | lg`, props `fullWidth`, `loading`), `components/ui/Input.tsx` (`Input`, `Textarea`), `Label`, `Badge`, `Card`, `FormMessage` (`<FormMessage error={sp.error} />`), `components/referrals/StatusBadge.tsx`.
- Design tokens (Tailwind): colors `ecrn-ink` (text), `ecrn-secondary` (muted text), `ecrn-line` (borders), `ecrn-paper` (page bg), `ecrn-green`, `ecrn-green-text`, `ecrn-action-surface`, `ecrn-selected`, `cobalt`, `navy`, `delta-surface`, `ecrn-reward-tint`; fonts `font-display` (Geist, headings/numbers), `font-mono` (eyebrows); class `t-eyebrow`. Rounded 14–16px cards, 1px `border-ecrn-line`, no heavy shadows. Admin is **desktop-first** but must not break on a phone.
- Copy: plain, short, sentence case. No em dashes in UI text. Money is stored in **cents**.
- Admin sidebar links already exist for: `/admin`, `/admin/routing`, `/admin/activity`, `/admin/members`, `/admin/candidates`, `/admin/team`, `/admin/jobs`, `/admin/applications`, `/admin/referrals`, `/admin/payouts`, `/admin/companies`, `/admin/sync` (labelled "Integrations"), `/admin/settings`.

Enums: `application_status` = submitted|reviewing|interviewing|offer|hired|rejected|withdrawn · `candidate_source` = referred|direct_application|admin_import|company_submission|self_signup · `company_lead_status` = new|contacted|qualified|engaged|won|lost|archived · `duplicate_status` = unique|pending_review|confirmed_duplicate|overridden_primary · `job_status` = draft|open|paused|filled|archived · `job_urgency` = low|normal|high|critical · `payout_status` = pending|approved|paid|denied|disputed · `referral_status` = submitted|duplicate_review|new|contacted|qualified|not_qualified|submitted_to_job|interviewing|offer_stage|placed|payout_pending|payout_approved|payout_paid|rejected|inactive · `staff_role` = owner|account_manager|recruiter · `user_role` = admin|referral_partner|candidate|company_contact (members are `referral_partner` or `candidate`; treat both simply as "member").

Foreign keys you can embed with PostgREST (examples):
`candidates → staff` twice, so name the FK: `account_manager:staff!candidates_account_manager_id_fkey(id, first_name, last_name)`, `recruiter:staff!candidates_recruiter_id_fkey(...)`. Same pattern for `job_applications_account_manager_id_fkey`, `job_applications_recruiter_id_fkey`, `job_referrals_account_manager_id_fkey`, `job_referrals_recruiter_id_fkey`, `jobs_account_manager_id_fkey`, `profiles_recruited_by_staff_id_fkey`, `staff_manager_id_fkey`. `jobs → job_private`: `private:job_private(client_company, internal_notes)`. PostgREST returns at most 1,000 rows per request: paginate with `.range()` or aggregate in SQL.

Existing RPCs (call with `sb.rpc(name, args)`):
- `admin_assign(p_entity text, p_id uuid, p_account_manager uuid, p_recruiter uuid)`: `p_entity` is `candidate` | `job_application` | `job_referral`. If only a recruiter is given, their manager becomes the account manager. Logs an `assigned` activity.
- `admin_route_unassigned()` → int: re-runs automatic routing for everyone without an owner.
- `resolve_invite_code(p_code text)` → `{kind: 'staff'|'member', code, name, title?}` or null (callable signed-out).
- `claim_invite_code(p_code text)` → `{name}` (a signed-in member links themselves to a recruiter).
- Member-side: `submit_referral`, `apply_to_job`, `complete_onboarding`, `set_my_resume`, `delete_my_account`, `search_places`, `nearest_place`.

Routing rules implemented in the database (`private.route_candidate`): (1) job owner, (2) the recruiter credited with the person's (or their referrer's) sign-up, with that recruiter's manager as account manager, (3) an account manager whose `territories` include the person's state (specialty match breaks ties), else unassigned. A manual or Bullhorn assignment is never overwritten.

Activity log actions in use: `account_created`, `onboarding_completed`, `role_set`, `referral_submitted`, `duplicate_detected`, `referred_to_job`, `application_submitted`, `status_changed` (metadata `{from, to}`), `note_added`, `primary_referrer_reassigned`, `routed` (metadata `{account_manager_id, recruiter_id, reason, job_id}`), `assigned`, `invite_code_claimed`, `account_deleted`.

Outbound sync: triggers write events to `integration_outbox` (`candidate.created|updated`, `referral.created`, `job_referral.created|updated`, `application.created|status_changed|assigned`, `company_lead.created`, `member.onboarded`); payloads include `owner` and `recruiter` objects `{ecrnId, name, email, role, bullhornUserId}`. `lib/integrations/staffing-referrals.ts` maps them to Bullhorn-shaped JSON and POSTs to `STAFFING_REFERRALS_WEBHOOK_URL` when configured.
